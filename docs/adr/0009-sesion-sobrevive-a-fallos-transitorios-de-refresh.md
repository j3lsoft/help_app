# La sesión sobrevive a fallos transitorios de refresh

Contexto: ante un 401 de una petición autenticada, `authInterceptor` intenta refrescar la sesión y, si el refresh falla, llamaba `authState.logout()` sin mirar el motivo (`src/app/core/interceptors/auth.interceptor.ts`). Un backend reiniciándose o un cambio WiFi↔datos hace que el `POST /api/v1/auth/refresh` devuelva 0 o 5xx —fallos que no dicen nada sobre la validez de las credenciales— y ese `catchError` deslogueaba igual: el usuario perdía el draft del Composer y cualquier trabajo en vuelo, y un reinicio del backend deslogueaba a todos los usuarios a la vez.

Decidimos: desloguear **solo** cuando el refresh falla de forma concluyente, es decir con `401` o `403`; ante cualquier otro fallo conservamos la sesión y propagamos el error. La condición se evalúa normalizando el rechazo con `toAppError(...)` (`core/utils/app-error.utils.ts`), porque lo que rechaza puede ser un `AppError`, un `Error` plano o cualquier otra cosa, y solo `401`/`403` cuentan como credenciales inválidas. El error que se propaga es `toAppError(refreshError)`, así el caller siempre recibe un `AppError` con el status real (0 para lo desconocido) y las páginas deciden con información veraz en vez de con un 401 fingido. El `logout()` del reintento (`retryWithToken`) se mantiene: un 401 con un token recién emitido sí es evidencia concluyente, y su chequeo se unifica vía `toAppError`. `errorInterceptor` pasa a respetar el contrato de `handled`: si recibe un `AppError` ya marcado, lo re-lanza sin re-adaptarlo ni volver a notificar.

Considered Options: desloguear solo con 401 (rechazado: un 403 de cuenta bloqueada o deshabilitada tampoco es recuperable, así que dejaría la sesión en un estado muerto); incluir 400/404/422 como conclusivos (rechazado: son ambiguos —payload malformado o bug— y desloguear por algo no concluyente reintroduce el bug que arreglamos); reintentar el refresh antes de rendirse (aplazado: el `errorInterceptor` ya reintenta GETs y `TokenRefreshService` coalesce refrescos concurrentes; añadirlo aquí amplía el radio de impacto sin que la issue lo pida); cooldown o circuit breaker para no repetir el ciclo 401→refresh fallido (rechazado por ahora: introduce estado y ventanas de token viejo silenciosas); propagar el 401 original en vez del error del refresh (rechazado: haría que las páginas mostraran un "no autorizado" falso y activaran ramas de negocio equivocadas). No se añade ningún término a `CONTEXT.md`: sesión, refresh y access token son infraestructura, no vocabulario del dominio Post/Profile.

Consequence: un fallo transitorio de refresh ya no navega a `/auth/sign-in` ni limpia el draft. La petición original falla con el error del refresh (status 0/5xx), que queda visible **una sola vez**: el toast lo emite el propio POST de refresh a través de `errorInterceptor`, que al respetar `handled` evita la re-adaptación y la cascada de avisos —antes eran toast interno + toast externo + mensaje de la facade para un mismo fallo—. Mientras el refresh no se recupere, cada acción posterior puede repetir el ciclo 401→refresh→fallo→aviso; se acepta como feedback honesto y de baja frecuencia, y `TokenRefreshService` ya coalesce los refrescos concurrentes. `BaseErrorFacade` sigue omitiendo los errores ya manejados, así que las páginas no duplican la notificación. La matriz de regresión vive en `auth.interceptor.spec.ts` (401 y 403 desloguean; 0, 5xx y errores no-HTTP conservan sesión) y en el nuevo `error.interceptor.spec.ts` (un `AppError` ya `handled` no se re-adapta ni tosta; un `HttpErrorResponse` 5xx sí).
